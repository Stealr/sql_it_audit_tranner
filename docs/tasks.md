# Задания SQL-тренажёра для ИТ-аудита

Первые 12 заданий на одной вымышленной базе SQLite. Порядок – от простой выборки к соединениям, группировке и проверке отсутствия записей. Условия не содержат готовых запросов.

## Общие правила

- Выводите только перечисленные поля в указанном порядке. Имена столбцов при проверке не учитываются.
- Повторяющиеся строки сохраняются, если не сказано иное. Порядок строк важен только при явно указанной сортировке.
- `accounts.is_active`: `1` – активна, `0` – отключена. `employees.status`: `active` или `terminated` (уволен).
- `NULL` в `assets.owner_employee_id` означает, что владелец не назначен.

## Учебная схема

| Таблица | Поля | Смысл |
| --- | --- | --- |
| `employees` | `id`, `full_name`, `status` | Сотрудники. |
| `systems` | `id`, `name` | Информационные системы. |
| `accounts` | `id`, `employee_id`, `system_id`, `login`, `is_active` | Учётные записи; `employee_id` может быть `NULL`. |
| `roles` | `id`, `name`, `is_privileged` | Роли; `1` означает привилегированную. |
| `account_roles` | `account_id`, `role_id` | Назначения ролей. |
| `assets` | `id`, `asset_tag`, `owner_employee_id`, `system_id` | Активы и владельцы. |
| `journal_entries` | `id`, `entry_date`, `amount`, `created_by_account_id` | Проводки; дата `YYYY-MM-DD`, сумма в целых рублях. |
| `approvals` | `id`, `entry_id`, `decision`, `approver_account_id` | Решения по проводке: `approved` или `rejected`; решений может быть несколько. |

Поля с суффиксом `_id` ссылаются на `id` соответствующей таблицы. `owner_employee_id` ссылается на `employees.id`, `created_by_account_id` и `approver_account_id` – на `accounts.id`, `entry_id` – на `journal_entries.id`.

## Задания

### 1. Активные учётные записи

**Навык:** `SELECT`, `WHERE`. Выведите активные учётные записи: `accounts.id`, `accounts.login`. Сортировка по `id` по возрастанию.

**Подсказка:** признак активности находится в `accounts.is_active`.

### 2. Уволенные сотрудники

**Навык:** фильтрация и сортировка. Выведите уволенных сотрудников: `employees.id`, `employees.full_name`. Сортировка по `full_name`, затем `id`, по возрастанию.

**Подсказка:** сравните `status` с точным значением из общих правил.

### 3. Активы без владельца

**Навык:** проверка `NULL`. Найдите активы без назначенного владельца: `assets.id`, `assets.asset_tag`. Сортировка по `id` по возрастанию.

**Подсказка:** используйте `IS NULL`.

### 4. Учётные записи без сотрудника

**Навык:** `LEFT JOIN`. Найдите учётные записи без соответствующей строки в `employees`. Учитывайте как `employee_id = NULL`, так и ссылку на несуществующий `employees.id`. Результат: `accounts.id`, `accounts.login`. Сортировка по `id` по возрастанию.

**Подсказка:** при соединении сохраните все строки из `accounts`.

### 5. Активный доступ уволенных сотрудников

**Навык:** `JOIN`. Найдите активные учётные записи уволенных сотрудников: `employees.full_name`, `accounts.login`. Сортировка по имени, затем по логину, по возрастанию.

**Подсказка:** нужны два условия – статус сотрудника и активность записи.

### 6. Активы уволенных сотрудников

**Навык:** соединение и фильтрация. Найдите активы, владельцами которых указаны уволенные сотрудники: `assets.asset_tag`, `employees.full_name`. Сортировка по `asset_tag` по возрастанию.

**Подсказка:** соедините актив с его назначенным владельцем.

### 7. Привилегированные роли

**Навык:** соединение трёх таблиц. Выведите каждое назначение привилегированной роли активной учётной записи отдельной строкой: `accounts.login`, `roles.name`. Сортировка по логину, затем названию роли, по возрастанию.

**Подсказка:** `account_roles` связывает учётные записи и роли.

### 8. Активные учётные записи по системам

**Навык:** `LEFT JOIN`, `GROUP BY`, `COUNT`. Для каждой системы, включая систему без активных записей, выведите `systems.name` и число активных учётных записей. Сортировка по имени системы по возрастанию.

**Подсказка:** условие активности в `WHERE` может исключить систему с нулём записей.

### 9. Дубли логинов в одной системе

**Навык:** `GROUP BY`, `HAVING`. Найдите пары «система – логин», встречающиеся более чем у одной учётной записи независимо от активности. Выведите `systems.name`, `accounts.login`, число записей. Сортировка по имени системы, затем логину, по возрастанию. Один логин в разных системах дублем не считается.

**Подсказка:** группируйте по системе и логину одновременно.

### 10. Несколько активных записей у сотрудника

**Навык:** группировка после соединения. Найдите сотрудников с двумя или более активными учётными записями в любых системах. Выведите `employees.full_name` и число активных записей. Сортировка по числу по убыванию, затем по имени по возрастанию.

**Подсказка:** исключите отключённые записи до подсчёта.

### 11. Проводки без одобрения

**Навык:** `NOT EXISTS` или эквивалентное антисоединение. Найдите проводки без единого решения `approved`: как без решений, так и только с `rejected`. Выведите `journal_entries.id`, `entry_date`, `amount`. Сортировка по `id` по возрастанию.

**Подсказка:** наличие хотя бы одного `approved` исключает проводку, даже если есть и `rejected`.

### 12. Крупные проводки без одобрения

**Навык:** сочетание фильтров и соединений. Найдите проводки на сумму от 100 000 рублей включительно без единого решения `approved`. Выведите `journal_entries.id`, `accounts.login` создавшей записи, `journal_entries.amount`. Сортировка по сумме по убыванию, затем по `id` по возрастанию.

**Подсказка:** используйте критерий из задания 11 и связь `created_by_account_id`.

## Данные для проверки

При наполнении базы нужны положительные и отрицательные примеры для каждого задания: отключённая запись уволенного сотрудника; запись с `NULL` и с несуществующим `employee_id`; система без активных записей; один логин в разных системах и дубль в одной; проводка с `rejected` и `approved` одновременно. Эталонные результаты следует получать из данных и проверять несколькими вариантами корректных запросов. Текст SQL не служит критерием оценки.
