# План разработки SQL-тренажёра

Цель – довести текущий прототип до работающего тренажёра с 12 заданиями из [tasks.md](tasks.md). Интерфейс опирается на [Lo-Fi макеты в Figma](https://www.figma.com/design/hSPaaGumGPeiOgNoIpIQRA/sql-trainer?node-id=0-1). Каждая итерация заканчивается работающей сборкой и проверкой перечисленных сценариев. Сравнение вариантов делаем на коротком прототипе или на уже созданных макетах, фиксируем выбор в этом файле перед реализацией следующего шага.

## Итерация 1. Данные и первые задания

- Описать задания единым типом: условие, доступные таблицы, начальный SQL, подсказка, ожидаемые поля и правило сортировки.
- Расширить вымышленную базу до схемы из `tasks.md`; добавить данные для заданий 1–3.
- Сделать каталог, открытие задания и переход между первыми тремя заданиями. SQL выполняется на свежей базе; условие остаётся на экране.
- **Сравнить идеи:** одна общая база для всех заданий и отдельная база для каждого. Критерии – понятность связей, простота добавления задания и независимость учебных данных. Записать принятое решение здесь.

**Готово, когда:** задания 1–3 открываются из каталога, запросы выполняются, данные после повторного запуска не меняются.

## Итерация 2. Таблицы рядом с редактором

- Добавить панель со всеми доступными таблицами, полями и типами данных.
- Показывать несколько строк выбранной таблицы, сохраняя видимыми условие и SQL-редактор.
- Подключить задания 4–6 и их данные; проверить случаи отсутствующего сотрудника и уволенного владельца.
- **Сравнить идеи:** раскрытие строк прямо в правой панели и отдельное окно просмотра. Критерии – видимость редактора, читаемость полей, число действий. Исходный вариант для проверки – правая панель из Lo-Fi макета.

**Готово, когда:** можно узнать схему и посмотреть строки любой таблицы, не теряя контекст задания и введённый SQL.

## Итерация 3. Проверка ответа

- Сделать кнопку «Проверить»: сравнивать значения строк результата с эталоном, включая повторы; порядок учитывать только по правилу задания. Текст SQL не сравнивать.
- Показать состояния «верно», «неверно», SQL-ошибка и подсказку из макетов.
- Подключить задания 7–8. Проверить несколько разных корректных запросов и типичные неверные ответы.
- **Сравнить идеи:** хранить готовые эталонные строки или вычислять их эталонным запросом на исходной базе. Критерии – воспроизводимость, простота обновления данных и диагностика ошибки в задании. Зафиксировать выбор до наполнения оставшихся заданий.

**Готово, когда:** альтернативные правильные запросы получают одну оценку, лишние или пропущенные строки дают понятный отказ, ошибка SQL не ломает экран.

## Итерация 4. Агрегация и прогресс

- Подключить задания 9–10 с данными для дублей логинов и подсчёта активных записей.
- Сохранять последний запрос отдельно для каждого задания и отмечать завершённые задания в `localStorage`.
- Добавить экран завершения задания и обновление прогресса в каталоге.

**Готово, когда:** прогресс и запросы восстанавливаются после перезагрузки страницы; подсчёты корректны для дублей и нулевых значений.

## Итерация 5. Проводки и итоговая проверка

- Подключить задания 11–12 и данные для проводок без решений, только с `rejected`, а также с `rejected` и `approved` одновременно.
- Пройти все 12 заданий несколькими корректными вариантами запросов; проверить неверные результаты, `NULL`, повторы строк и сортировку.
- Проверить рабочую область на узком экране: условие должно оставаться доступным, переключение таблиц не должно стирать SQL.

**Готово, когда:** все 12 заданий можно открыть, выполнить и проверить; прогресс сохраняется; `npm run build` проходит.

## Принятые решения

### Итерация 1 – одна общая база

Сравнили общую базу с отдельной базой для каждого задания. Общая база сохраняет одни и те же связи между сотрудниками, системами, учётными записями и активами; новое задание добавляется без копирования схемы и пересборки похожих данных. Отдельные базы лучше изолировали бы наборы данных, но усложнили бы поддержку общей учебной схемы. Выбрали **общую базу** в `src/data/seed.sql` с созданием новой копии перед каждым запуском запроса. Изменения данных проверяются тестами заданий 1–3, чтобы дальнейшее наполнение не сломало ранние упражнения.

Коммит итерации 1: `9317703`.

### Итерация 2 – просмотр в правой панели

Сравнили просмотр строк в правой панели с отдельным модальным окном на Lo-Fi макетах. Модальное окно перекрывало SQL-редактор; встроенный просмотр оставляет условие и запрос на экране и требует меньше переключений. Выбрали **встроенный просмотр**: список таблиц прокручивается отдельно, строки выбранной таблицы показаны под ним. На невысоких экранах боковые панели закреплены и прокручиваются внутри.

### Итерация 3 – эталонный запрос

Сравнили хранение готовых эталонных строк с вычислением эталона SQL-запросом на исходной базе. Готовые строки проще читать, но при добавлении данных их нужно обновлять вручную для каждого затронутого задания. Выбрали **эталонный запрос** в описании задания: он выполняется до запроса пользователя на свежей базе, а проверка сравнивает только таблицы результатов. Эталон и данные покрыты проверками, поэтому изменение набора данных не должно незаметно менять оценку.

## Итоговая проверка

Все пять итераций выполнены. Для каждого из 12 заданий тесты проверяют эталонный запрос, альтернативное решение и отклонение стартовой заготовки. Отдельно проверены повторы строк, `NULL`, сортировка и порог в 100 000 рублей. В браузере проверены восстановление запроса и прогресса после перезагрузки, а также переходы между условием, редактором и просмотром таблиц на экране шириной 390 пикселей.
